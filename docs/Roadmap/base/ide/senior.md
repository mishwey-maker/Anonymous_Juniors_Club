## Senior: «Определяю стандарт и масштабирую»

На Senior-уровне редактор — это элемент инфраструктуры документации. Вы не просто настраиваете VS Code для себя или команды, вы определяете, какой редактор использовать в организации, как он интегрируется с CI/CD и как обеспечить консистентность между командами. Вы также понимаете альтернативы VS Code и можете обосновать выбор: JetBrains Writerside с гибридным Markdown + XML, специализированные HAT вроде MadCap Flare или лёгкие редакторы для контрибьюторов.

Что входит в Senior-уровень:

* **Стратегия выбора редактора:** обоснование выбора VS Code vs. JetBrains Writerside vs. специализированные HAT (MadCap Flare, Adobe RoboHelp) в зависимости от задач. Writerside предлагает гибридный Markdown + semantic XML, topic-based authoring и интеграцию с Git, но после закрытия standalone-IDE в марте 2025 остаётся только как бесплатный плагин для JetBrains IDE с более консервативным roadmap.

* **Интеграция с CI/CD:** настройка редактора так, чтобы локальные проверки совпадали с проверками в CI (одинаковые версии линтеров, одинаковые правила). Если Vale чисто проходит на вашем ноутбуке, он должен так же проходить в GitHub Actions — иначе PR будет «красным» без причины.

* **ИИ-ассистенты:** подключение GitHub Copilot, настройка контекста через .github/copilot-instructions.md для определения стандартов документации, понимание ограничений и безопасности при работе с конфиденциальной документацией.

* **Стандартизация:** создание org-wide шаблона .vscode/ для всех документационных репозиториев: settings.json (поведение редактора, форматирование при сохранении), extensions.json (рекомендуемые расширения), tasks.json (скрипты сборки и проверок), snippets (шаблоны блоков).

* **Обучение:** проведение воркшопов для инженеров и писателей по настройке редактора, создание внутренних гайдов, чтобы новый автор мог за 15 минут получить рабочую среду, а не полдня искать расширения.

*Ключевой принцип Senior: вы определяете, как выглядит «стандартная среда технического писателя» в организации, и отвечаете за её поддержку. Если инженер или писатель открывает репозиторий и получает готовую среду без ручной настройки — это ваша работа.*

## Курсы и книги (Senior)

[JetBrains Writerside Review: Is It Worth Using in 2026? (Docsio)](https://docsio.co/blog/writerside) - Детальный разбор Writerside: гибридный Markdown + XML, topic-based authoring, что изменилось после закрытия standalone-IDE в 2025 году, ограничения и сравнение с Docusaurus, Mintlify и Starlight. Помогает обосновать выбор редактора для организации;

[5 .vscode Files That Standardize Your Whole Team (Towards AI)](https://pub.towardsai.net/5-vscode-files-that-standardize-your-whole-team-f6e1e80fbf5f) - Практический гайд по стандартизации VS Code для команды: settings.json, extensions.json, launch.json, tasks.json и snippets. Показывает, как закоммитить .vscode в Git, чтобы каждый новый автор получал готовую среду;

[Write Better with Vale (Brian P. Hogan)](https://books.google.com.sg/books?id=nMabEQAAQBAJ) - Книга, которая связывает редактор и CI: как превратить стайлгайд в исполняемые правила Vale, интегрировать их в VS Code, Git hooks и CI pipeline. Ключевой ресурс для обеспечения идентичных проверок локально и в CI;

[VS Code Documentation: Tasks]() - Официальный гайд по tasks.json: как запускать сборку документации, проверку ссылок и линтеры из редактора одной командой, чтобы локальный workflow совпадал с CI;

[GitHub Copilot: Custom Instructions (VS Code Docs)](https://code.visualstudio.com/docs/editor/tasks) - Официальная документация по настройке .github/copilot-instructions.md: как задать стандарты документации, стиль и требования к формату, чтобы Copilot генерировал контент, соответствующий вашим правилам.
